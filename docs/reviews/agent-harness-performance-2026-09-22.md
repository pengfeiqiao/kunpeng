# Agent / Harness 性能对比与第二轮优化

审阅日期：2026-09-22。本轮针对现有鲲鹏实现做局部优化，没有替换 agent、改模型路由或新增界面按钮。

## GitHub 源码对比

- [OpenAI Codex：流式控制器](https://github.com/openai/codex/blob/main/codex-rs/tui/src/streaming/controller.rs) 将已稳定正文与可变尾部分开，缓存稳定区渲染，并用队列控制提交。鲲鹏已存在 80ms store 合并、抽屉节流和稳定 Markdown 前缀，因此不重复叠加全局节流。本轮处理的是已完成回复仍被父级更新带动重渲染的问题，添加回复/正文缓存，并缩小项目状态订阅范围。
- [OpenCode：会话状态层](https://github.com/anomalyco/opencode/blob/dev/packages/app/src/context/server-session.ts) 使用消息分页、按身份维护状态、批量状态更新和请求去重。鲲鹏已有尾部消息窗口，但筛选窗口之前，每次输入都会遍历全部历史并反复扫描队列。本轮把回执归属建成索引、缓存历史投影，保留旧上下文恢复逻辑，且显式 messageId 回执优先于文本猜测。
- [Pi：会话管理](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/src/core/session-manager.ts) 常规会话条目以 JSONL 追加，并维护 ID 索引。可借鉴的原则是避免为每次增量重写所有历史。上一轮已经将鲲鹏项目历史拆成独立载荷，本轮继续避免输入时重算稳定的目标、消息和上下文。没有直接照搬 Node 同步文件 API 到 Tauri 渲染线程，也没有把现有会话存储仓促迁移为 JSONL。

以上为源码阅读后的工程取舍，并非对这三个产品的整体性能排名。

## 本轮落地

1. **历史消息投影**：`projectAssistantHistory` 一次建立 messageId 和精确文本索引，`useMemo` 按消息/队列条目变化重新计算。草稿每次按键不再重新匹配全部历史；换对象时只筛选已建索引。项目、会话、对象、输出类型及授权范围仍参与归属。
2. **输入目标缓存**：保持未变化草稿目标的引用稳定；声音助手内容未变化时复用原目标，真正内容变化仍重新捕获修订，排队消息执行前仍做严格校验。画布目标缓存依赖真实节点与选择状态，避免使用陈旧目标。
3. **回复渲染隔离**：缓存已完成回复与 Markdown；消息组件只订阅项目 ID、对象注册表、对应快照，不因单纯视图选择变化重新渲染全部正文。
4. **项目上下文缓存**：按实际记忆项目、项目名、规格和接入材料引用重建，而不是在每一次工坊状态发布时重新拼装。只保留最近一次缓存，不积累历史项目。
5. **流式事件队列**：Anthropic 兼容通道和 DeepSeek OpenAI 兼容通道换用摊销 O(1) 队列，消费后立即释放对应槽位。突发流式数据每处理一小批检查 8ms 工作预算，超出时通过任务边界让出主线程；不是只 await 已完成 Promise。
6. **终止完整性**：修复 Anthropic 通道以“传输结束标记”直接控制消费循环的问题。现在按序消费到终止事件，避免完成/错误事件先到导致队列尾部正文、工具参数或错误丢失；主动取消仍优先退出。
7. **监听清理**：DeepSeek 兼容通道的监听注册纳入 try/finally，部分注册失败也会清理之前的监听；已取消调用不再启动请求。

没有改动锁定的 DSH 上游代码，也没有执行付费生成或自动重放。

## 可复现合成基准

运行 `node scripts/benchmark-agent-responsiveness.mjs`。不读用户项目、不联网、不使用凭证。以下为本机 3 次运行中位数；历史输入是每轮用户/助手两条消息、稳定回执及合成创作上下文。

| 工作量 | 原实现 | 新实现 |
| --- | ---: | ---: |
| 100 轮历史归属计算 | 3.83ms | 0.18ms |
| 500 轮历史归属计算 | 76.18ms | 1.04ms |
| 1,000 轮历史归属计算 | 316.25ms | 1.82ms |
| 100,000 条积压事件队列入队/消费 | 808.05ms | 2.89ms |

新历史索引只在输入数据变化时构建，正常输入草稿还会复用上述结果。合成流式 JSON 负载 100,000 条产生 3 次任务让步，测得最长工作片段约 8.13ms；这不是浏览器实际帧率或对真实网络负载的硬时延保证。单个巨大 JSON/SSE 解析、操作系统调度仍可能超出预算。

## 回归与边界

最终验证：`npm run test:harness` 873 项全部通过；`npm run test:conversation` 14 项通过、1 项可选截图跳过；`npm run build` 通过（保留既有 bundle 体积提示）。

- 流式回归覆盖结束先到、1,000 个积压片段、工具 JSON 完整性、错误传播、缓冲中止、提前停止消费、部分监听注册失败、预取消调用零请求。
- 历史回归覆盖跨对象、项目隔离、同文消息、旧记录恢复及 1,000 条队列只序列化 1,000 次；原声音助手连续修改回归保留。
- 性能数字来自合成负载，不能解释为整个鲲鹏快了同样倍数；也不能据此宣称所有用户卡顿都已消失。
- 超大项目首次加载仍会读取历史；图片/视频解码、原生 IPC 和用户机器内存压力需要现场项目验证。本轮没有通过删除历史或削减生成质量换速度。
- 本轮为源码及构建验证，没有安装替换现有应用。
